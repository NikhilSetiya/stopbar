# ADR 0004: Signed approvals replace API-key approval

- Status: **Accepted**
- Date: 2026-11-24
- Task: CS-151 (issue #32)
- Spec: [`spec/approval-signature-v1.md`](../../spec/approval-signature-v1.md)

## Context

Escalation approval and circuit-breaker reset (CS-124, #128) were both
authorised by an API key with an `approve` scope: whoever held that bearer
secret and called the endpoint counted as an approver, one vote per
authenticated identity. An API key authenticates a *request* to stopbard; it
was never meant to authenticate a *decision*, and it carries no signature a
third party can check offline, audit, or hold the approver to later. A
compromised or overly-scoped API key could approve or reject anything, or
vote to reopen a tripped breaker, with no cryptographic binding to what was
actually approved. Issue #32 asks for the replacement this ADR records:
Ed25519 approver keys, held only by the approver, countersigning the exact
thing being decided.

## Decision

1. **A new, separate credential.** Approver keys are Ed25519, generated by
   `stopbar approver keygen` and held only by the approver (CLI signs
   locally; the private key never leaves the machine). They live in their own
   tagged file format (`stopbar-approver-key-ed25519-v1\n`), distinct from
   decision keys and wallet keys, so none of the three can be loaded as
   another. `stopbard` is configured with the approver *public* keys only
   (config file and/or flag), each bound to a tenant and an id.
2. **The signature covers the decision, not the request.** An escalation
   approval signs `{escalation_id, payload_hash, decision, expiry}`; a
   breaker reset signs `{tenant, trip_request_id, decision, expiry}`
   (`spec/approval-signature-v1.md` §2–§4). Both are domain-separated,
   JCS-canonical Ed25519 signatures — not a JWS, since there is one fixed
   algorithm and no third party parses the envelope generically the way a
   decision-token adapter does.
3. **M-of-N, distinct keys, with a floor.** A quorum of `M` distinct
   approver keys is required for both escalation approval and breaker reset,
   replacing #128's per-identity vote count with the same rule enforced
   cryptographically. `M` ≥ 2 unless `stopbard` is run with `-dev-world`; it
   refuses to start otherwise. A second vote from a key that already holds a
   live one is refused, not double-counted. Any valid reject resolves an
   escalation immediately, regardless of quorum (`internal/approval.Tally`).
4. **Expiry is checked at verification time, not issuance time.** The object
   carries no `iat`. A signature counts only while `now < expiry ≤ now + 1h`,
   checked by the verifier's own clock, so nothing needs to trust how long ago
   it was signed.
5. **Separation of duties stays explicit.** A requester cannot approve its
   own escalation. Because approver keys and API keys are different
   credential types, the binding is a configured `agent_id` on the approver
   entry (`spec/approval-signature-v1.md` §7); when it matches the
   escalation's requester, approval (not reject) is refused.
6. **API keys are removed from approval entirely.** `/v1/approvals/*` and
   `/v1/breakers/*/reset` accept signed envelopes; an API key, having no
   Ed25519 key pair, can never appear in the configured approver set and so
   can never produce a valid signature. CS-151/152's existing single-approver
   `Engine.Approve(ctx, id, approver string)` and CS-124's identity-string
   `Limiter.ResetBreaker` are re-pointed at verified, quorum-resolved
   approvals rather than an authenticated API-key identity.

## Consequences

- An approval or reset is now independently auditable and verifiable
  offline, by anyone holding the configured public keys — the same offline
  property `stopbar audit verify` already gives decision tokens and the
  audit log.
- Holding the quorum requirement to the breaker's existing floor
  (`model.MinBreakerQuorum` = 2) means one operator cannot unilaterally
  approve an escalation or reopen a tripped tenant; CS-151 extends that
  floor from breaker resets to escalation approvals.
- `internal/approval` is a new stdlib-only trusted-core package (Ed25519
  only), alongside `internal/canon` and `internal/decision`. It depends on
  `decision.Kid` for the RFC 7638 thumbprint construction, so there is one
  thumbprint rule in the codebase, not two; the key *files* and the key
  *sets* a verifier checks against stay separately tagged and never
  interchangeable.
- The quorum evaluator (`approval.Tally`) is pure and storage-agnostic; it
  does not decide how pending escalations or breaker trips are persisted,
  so it is identical for both flows and does not need to change when the
  pending-escalation storage (CS-152, PR #130) does.
- Existing demos and the Python SDK must move from a single API-key
  approval call to generating/holding two or more approver keys and signing
  locally; this lands with the integration (engine, gateway, CLI, SDKs,
  e2e) once CS-152's lifecycle endpoints are in place.
